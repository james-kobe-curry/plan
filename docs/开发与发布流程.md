# 开发与发布流程

仓库地址：https://github.com/james-kobe-curry/plan

本文档约定 plan 的开发环境、分支与提交规则、持续集成以及版本发布流程。产品取舍见 [开发日志](开发日志.md)，逐版用户变化见 [更新日志](../CHANGELOG.md)，操作说明见 [使用指南](使用指南.md)。

## 一、仓库约定

- `main` 是唯一长期分支，始终保持可构建、测试全部通过。
- Git 历史从 **1.12.1 基线**开始，不补造早期版本的提交或标签；早期版本只以安装包和源码包形式归档（见第八节）。
- 历史安装包、源码压缩包不进入 Git，统一通过 [GitHub Releases](https://github.com/james-kobe-curry/plan/releases) 分发；验证截图随仓库保存。
- 签名私钥、`local.properties`、构建缓存和设备数据永不提交。

## 二、开发环境

| 项 | 要求 |
| --- | --- |
| JDK | 17 或 21 |
| Android SDK | Platform 36、Build-Tools 36.0.0 |
| Gradle | 8.14.3（使用仓库自带 wrapper，无需单独安装） |
| AGP / Kotlin | 8.12.0 / 2.1.20 |
| 最低系统 | Android 8.0（minSdk 26），target/compile SDK 36 |
| IDE | Android Studio（打开仓库根目录即可） |

## 三、首次获取与本机配置

```powershell
git clone git@github.com:james-kobe-curry/plan.git
cd plan
```

1. 新建 `local.properties`，指向本机 Android SDK（该文件已被忽略，不提交）：

   ```properties
   sdk.dir=F\:\\DevData\\Android\\Sdk
   ```

2. 需要在本机构建 Release 时，在 `.signing/` 放置发布证书 `tongpin-release.jks` 和 `release.properties`（该目录已被忽略）。覆盖升级必须沿用同一证书；证书丢失后只能以新签名安装，无法覆盖旧版本。

   `release.properties` 格式：

   ```properties
   storeFile=.signing/tongpin-release.jks
   storePassword=***
   keyAlias=***
   keyPassword=***
   ```

3. 若本机全局 Gradle 缓存损坏，可追加独立缓存：`.\gradlew.bat --gradle-user-home .gradle-user`。

## 四、常用命令

```powershell
# 单元测试
.\gradlew.bat testDebugUnitTest

# Debug / Release 构建
.\gradlew.bat assembleDebug
.\gradlew.bat assembleRelease

# Lint（发布前 Debug、Release 都要跑）
.\gradlew.bat lintDebug lintRelease

# 发布前完整检查
.\gradlew.bat :app:testDebugUnitTest :app:lintDebug :app:lintRelease :app:assembleRelease
```

规则层代码（数据模型、日期、统计、备份事务等）必须配单元测试，测试位于 `app/src/test/java/com/tongpin/app`。涉及通知、真实出声、文件选择器、系统分享等设备行为的改动，还需在模拟器或真机上按验证记录逐项核对。

## 五、日常开发流程

1. 从 `main` 切出工作分支，命名表达意图：`feat/...`、`fix/...`、`docs/...`、`chore/...`。
2. 一个提交只做一件事。提交信息用中文写清**触发条件、最终行为和验证方式**，不要只写“优化”“修复问题”。例如：

   ```
   fix(focus): 计时偏好写入失败时回退内存状态

   持久化返回失败或抛异常时恢复原计时状态并提示错误，
   只有保存成功后才推进通知与完成确认；新增 FocusPersistenceTest 覆盖六类失败路径。
   ```

3. 本地至少跑通 `testDebugUnitTest`；改动界面或设备相关行为时补充模拟器核对。
4. 通过 Pull Request 合入 `main`；CI 全绿、核对无误后合并，合并后删除工作分支。
5. 用户可感知的行为变化同步更新 `README.md` 和 `CHANGELOG.md`；产品取舍或存储、迁移决策记入 `docs/开发日志.md`。

## 六、持续集成（CI）

推送 `main`、提交 Pull Request 或推送 `v*` 标签时，GitHub Actions（`.github/workflows/ci.yml`）自动执行：

1. JDK 17 + Android SDK 36 环境；
2. `testDebugUnitTest` 全部单元测试；
3. `lintDebug` 静态检查；
4. `assembleDebug` 构建，并把 Debug APK 作为构建产物上传。

CI 必须通过才能合并。CI 不能覆盖通知准时性、真实扬声器出声、厂商后台策略和第三方分享接收，这些仍按验证记录在模拟器与真机上核对。

## 七、版本发布流程

应用版本、`versionCode` 与数据格式版本**分开管理**：只有持久化结构改变时才升级数据格式（JSON/ZIP）版本，并写明缺省值、旧版读取与恢复规则。

每次发布按下列清单执行：

1. **定版本号**：遵循语义化版本
   - 补丁（兼容修复，不改数据格式）：递增最后一位，如 1.12.1 → 1.12.2，`versionCode` +1；
   - 功能版本：递增次版本号，`versionCode` +1；
   - 在 `app/build.gradle.kts` 同步 `versionName` 与 `versionCode`。
2. **更新文档**：
   - `README.md` 的“当前版本”和“本版更新”；
   - `CHANGELOG.md` 增加版本段落（修复/新增、验证结果）；
   - 新建或更新 `docs/验证记录.md`，保留执行命令、结果、截图与验证边界。
3. **完整验证**：执行第四节的发布前完整检查命令，要求测试 0 失败、0 错误、0 跳过，记录 lint 警告数量（不得把“0 错误”写成“0 警告”，不靠新增 ignore 隐藏警告）。
4. **模拟器/真机核对**：覆盖升级安装（升级前后主数据逐字节一致）、主要流程和本次改动路径。
5. **构建与校验**：产出 Release APK，验证签名与上一版证书一致、启动图标一致；计算 APK 与源码包的 SHA-256，写入 `deliverables/plan-<版本>-checksums.json`。
6. **源码包**：按白名单打包（源码、测试、资源、文档、截图、工具、wrapper；不含 `.signing/`、`local.properties`、`build/`、缓存与设备数据），命名 `plan-<版本>-source.zip` 并逐文件核对。
7. **提交与标签**：提交以上变更，打附注标签：

   ```powershell
   git tag -a v1.12.2 -m "plan 1.12.2"
   git push origin main --tags
   ```

8. **发布 Release**：在 GitHub Releases 选择该标签，上传 APK、源码包和 checksums，发布说明取自 CHANGELOG 对应段落。
9. **发布后核对**：Release 资产可下载、校验值匹配、CI 标签构建通过。

## 八、历史版本归档

1.0.0–1.12.0 的安装包与源码包留存于 `deliverables/`（本地）并集中发布在 GitHub Releases 的 **“历史版本归档”** 中，关联 `legacy-archives` 标签。该标签仅用于挂载归档资产，**不代表对应版本的 Git 源码状态**；早期版本的真实源码以各自源码包为准，当前行为以 `main` 和文档为准。

## 九、不入库清单

以下内容不得提交（`.gitignore` 已覆盖大部分）：

- `.signing/`、`*.jks`、`*.keystore` 及任何证书密码；
- `local.properties`；
- `.gradle/`、`.gradle-user/`、`.dependency-cache/`、`.kotlin/`、所有 `build/` 目录；
- `*.log`、模拟器探测临时文件；
- `deliverables/*.apk`、`deliverables/*.zip`（走 Releases）；
- IDE 个人配置（`.idea/`、`*.iml`）与系统文件。
